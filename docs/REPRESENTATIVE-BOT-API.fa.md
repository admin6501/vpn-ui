# راهنمای API نمایندگان برای اتصال ربات تلگرام

این راهنما برای **VPN-UI v1.0.0** است. مخاطب آن برنامه‌نویس ربات فروش و نماینده‌ای است که مدیر پنل به او دسترسی داده است. API پنل ساخت و مدیریت سرویس را انجام می‌دهد؛ خودِ ربات باید پیام‌های تلگرام، محصولات، پرداخت، تأیید پرداخت، سفارش‌ها و ارسال لینک به مشتری را پیاده‌سازی کند. وجود ربات تلگرام داخلی پنل به‌تنهایی به معنی داشتن فروشگاه و درگاه پرداخت نیست.

> آدرس‌ها، شناسه‌ها و نام‌های این سند نمونه هستند. نام کاربری، رمز، کد دومرحله‌ای، کوکی، توکن تلگرام و لینک ساب واقعی را در گیت‌هاب، پیام گروهی یا لاگ ربات منتشر نکنید. برای ربات یک حساب نمایندهٔ مستقل با حداقل دسترسی بسازید و ارتباط با پنل را با HTTPS معتبر برقرار کنید.

## ۱. پیش‌نیازها و محدودیت‌ها

مدیر باید به نماینده حساب، نقش، گروه‌های مجاز و در صورت لزوم اعتبار یا سهمیه بدهد. نقش تعیین می‌کند چه عملی مجاز است؛ گروه‌ها و محدودهٔ مالکیت تعیین می‌کنند روی کدام کاربران و ورودی‌ها می‌توان عمل کرد. «همهٔ کاربران» فقط در صورت اعطای صریح آن محدوده مجاز است؛ آن را برای ربات فروش معمولی درخواست نکنید. اگر نقش، محدودیت تعداد کاربر، حجم حداقل/حداکثر یا محدودیت اعتبار داشته باشد، API همان محدودیت‌ها را اعمال می‌کند. فعال‌بودن سوییچ کاربر هم به‌تنهایی اثبات اتصال نیست؛ سهمیه، انقضا، دسترسی ورودی و وضعیت نماینده نیز مؤثرند.

مسیر پایه شامل **آدرس، پورت و مسیر مخفی پنل** است؛ `/panel/...` به انتهای آن اضافه می‌شود. مسیر ساب جداگانه پیکربندی می‌شود. مقادیر زیر صرفاً نمونه‌اند:

```sh
umask 077
BASE='https://panel.example.com:2053/EXAMPLE_PATH'
JAR="$(mktemp)"
chmod 600 "$JAR"
```

برای پاک‌کردن فایل کوکی پس از تست، `rm -f "$JAR"` را اجرا کنید؛ آن را در کنار کد ربات یا داخل مخزن قرار ندهید. ربات تولیدی کوکی را در محیط خصوصی نگه دارد و با انقضای نشست دوباره وارد شود. تعویض رمز، نام کاربری، وضعیت امنیتی یا لغو نشست می‌تواند کوکی را بی‌اعتبار کند.

## ۲. ورود و استفاده از نشست

پنل **API Key مستقل ندارد**. ابتدا `POST /login` بزنید، موفقیت پاسخ JSON را بررسی کنید و کوکی `vpn-ui` را برای درخواست‌های بعدی نگه دارید. اگر حساب ۲FA دارد، کد جاری در فیلد `twoFactorCode` لازم است. نمونهٔ زیر رمز و کد را بدون نمایش هنگام تایپ می‌پرسد؛ کد را تنها برای حساب دارای ۲FA وارد کنید:

```bash
read -r -p 'نام کاربری نماینده: ' PANEL_USER
read -r -s -p 'رمز نماینده: ' PANEL_PASSWORD; printf '\n'
read -r -s -p 'کد دومرحله‌ای، اگر فعال است: ' PANEL_OTP; printf '\n'
curl -sS -c "$JAR" -X POST "$BASE/login" \
  --data-urlencode "username=$PANEL_USER" \
  --data-urlencode "password=$PANEL_PASSWORD" \
  --data-urlencode "twoFactorCode=$PANEL_OTP"
unset PANEL_PASSWORD PANEL_OTP
```

پاسخ موفق معمولاً شکل `{"success":true,"msg":"...","obj":...}` دارد. وضعیت HTTP 200 به‌تنهایی کافی نیست: حتماً `success` را بررسی کنید. اگر رمز درست باشد ولی کد لازم ارسال نشود، پاسخ می‌تواند `success:false` و `obj.twoFactorRequired:true` داشته باشد. حسابی که مدیرش ثبت ۲FA را الزامی کرده ولی هنوز ثبت نکرده، تا تکمیل ثبت از صفحهٔ امنیت نمی‌تواند APIهای عادی را استفاده کند.

ربات باید کوکی و رمز را مثل کلید دسترسی محرمانه نگه دارد. اگر قرار است بدون حضور نماینده با ۲FA دوباره وارد شود، پیاده‌سازی آن به روش امن تولید کد و نگهداری راز TOTP نیاز دارد؛ صرف دادن یک کد شش‌رقمی موقت کافی نیست. پشتیبانی از ۲FA را با توسعه‌دهندهٔ همان ربات بررسی کنید.

در نمونه‌های بعد، هدر زیر و کوکی را به تمام درخواست‌ها می‌فرستیم:

```sh
curl -sS -b "$JAR" -H 'X-Requested-With: XMLHttpRequest' \
  "$BASE/panel/api/clients/list?page=1&size=20"
```

خطای ورود منقضی‌شده در `/panel/api/...` ممکن است `404` با بدنهٔ خالی باشد؛ 404 همیشه به معنی اشتباه بودن آدرس نیست. `403` یعنی مجوز یا محدوده کافی نیست و `429` می‌تواند به معنی محدودیت تعداد درخواست باشد. در مسیرهای `/panel/...` نیز هدر بالا مانع اشتباه‌گرفتن صفحهٔ HTML ورود با پاسخ API می‌شود. پاسخ، نوع محتوا، `success` و `msg` را بررسی کنید؛ پیام خطا را برای پشتیبان نگه دارید و اطلاعات حساس را در لاگ ننویسید.

## ۳. مجوزهای نقش نماینده و کاربرد در ربات

| مجوز نقش | کاربرد در ربات | محدودیت |
|---|---|---|
| مشاهدهٔ کاربران `users.read` | فهرست کاربران، جست‌وجو، مصرف و وضعیت اشتراک | محدودهٔ «مال خود» یا «همه» را مدیر تعیین می‌کند. |
| ساخت کاربر `users.create` | ساخت سرویس پس از تأیید سفارش | فقط با گروه و ورودی مجاز و در چارچوب اعتبار و محدودیت نقش. |
| ویرایش کاربر `users.update` | تغییر مشخصات، حجم، تاریخ، وضعیت و محدودیت‌های مجاز | محدودهٔ ویرایش مستقل از محدودهٔ مشاهده است؛ تغییر حجم/زمان می‌تواند هزینه داشته باشد. |
| حذف کاربر `users.delete` | حذف با تأیید نماینده | محدودهٔ حذف مستقل است؛ حذف روی یک ورودی لزوماً حذف تمام عضویت‌های حساب نیست. |
| ریست مصرف `users.reset_usage` | صفرکردن مصرف دوره | جدا از ویرایش است و ممکن است از اعتبار نماینده هزینه کسر شود. |
| لغو/تغییر اشتراک `users.revoke_sub` | اجازهٔ تغییر `subId` در ویرایش کاربر | مجوز ویرایش هم لازم است؛ تغییر شناسه لینک قبلی را تغییر می‌دهد و باید با احتیاط انجام شود. |

برای **تمدید**، هر دو مجوز ویرایش و ریست مصرف لازم است؛ محدودهٔ محدودتر از این دو اعمال می‌شود. مجوز خواندن با محدودهٔ همه، ویرایش یا حذف همه را مجاز نمی‌کند. در نقش‌های واردشده ممکن است مجوزهای دیگری مانند `system.read` یا `settings.update` هم وجود داشته باشد؛ آن‌ها به خودی خود مجوز مدیریت مشتریان یا مالک اصلی نمی‌دهند. مجوزها و محدودیت‌های واقعی را مدیر پنل تعیین می‌کند.

عملیات گروهی تغییر عضویت `/bulkMembership` برای حساب نمایندهٔ `IsReseller` رد می‌شود. انتقال مالکیت و فهرست انتخاب مالکان مخصوص سوپرادمین است. ساخت یا ویرایش اینباند، مدیریت هسته، نود، تنظیمات کل پنل، بکاپ و ری‌استارت را از قابل‌دسترس‌بودن فهرست کاربران نتیجه نگیرید. برخی حساب‌ها و نقش‌های خاص ممکن است دسترسی جداگانه‌ای داشته باشند؛ به خطا و سیاست مدیر احترام بگذارید و از حساب مالک برای دورزدن محدودیت استفاده نکنید.

## ۴. فهرست کاربران، گروه‌ها و اعتبار

تمام مسیرها نسبت به `$BASE` هستند و به کوکی معتبر نیاز دارند:

| روش | مسیر | کاربرد |
|---|---|---|
| GET | `/panel/api/clients/list?page=1&size=20&search=alice` | کاربران قابل مشاهده؛ جست‌وجو اختیاری است. |
| GET | `/panel/api/clients/groups` | گروه‌های قابل انتخاب و `inboundIds` هر گروه. |
| GET | `/panel/api/clients/assignable` | ورودی‌های قابل تخصیص به کاربر. |
| GET | `/panel/api/clients/inbounds` | اطلاعات ورودی‌های قابل مشاهده برای کارت کاربران. |
| GET | `/panel/api/clients/balance` | وضعیت اعتبار نماینده، مطابق مدل صورتحساب او. |
| GET | `/panel/api/server/status` | وضعیت سرور، در صورت اعطای دسترسی Overview / `system.read`. |
| GET | `/panel/api/server/userStats` | آمار کاربران در محدودهٔ مجاز حساب. |
| GET | `/panel/api/inbounds/getClientTraffics/:email` | مصرف کاربر مجاز؛ `email` باید URL-encode شود. |
| POST | `/panel/api/inbounds/onlines` | گزارش کاربران آنلاین مجاز. |
| POST | `/panel/api/inbounds/onlineMemberships` | گزارش عضویت‌های آنلاین مجاز. |
| POST | `/panel/api/inbounds/lastOnline` | آخرین فعالیت قابل مشاهده. |

نمونهٔ URL با email ساده:

```sh
curl -sS -b "$JAR" -H 'X-Requested-With: XMLHttpRequest' \
  "$BASE/panel/api/clients/groups"
curl -sS -b "$JAR" -H 'X-Requested-With: XMLHttpRequest' \
  "$BASE/panel/api/inbounds/getClientTraffics/alice"
```

از خروجی فهرست، `email`، `subId`، `groupIds` و `memberships` را طبق نیاز بخوانید. `memberships[].inboundId` شناسهٔ ورودی و `memberships[].clientId` شناسه‌ای است که ویرایش آن پروتکل در مسیر درخواست نیاز دارد. این شناسه همیشه ایمیل نیست. برای مصرف فعلی، آپلود و دانلود را با هم جمع کنید؛ `totalGB` در API **بایت** است، نه عدد گیگابایت. صفرِ محدودیت حجم یعنی نامحدود. `expiryTime` زمان یونیکس بر حسب **میلی‌ثانیه** است؛ صفر یعنی بدون انقضا و مقدار منفی برای شروع مدت از اولین استفاده به کار می‌رود. فعال‌بودن واقعی را با وضعیت سهمیه و انقضا هم بررسی کنید.

## ۵. ساخت مشتری بعد از پرداخت تأییدشده

ابتدا گروه مجاز را از `/clients/groups` و ورودی مناسب آن گروه را از `inboundIds` و `/clients/assignable` انتخاب کنید. نمونهٔ زیر فقط برای **یک ورودی VLESS** است: `id=3` باید واقعاً در گروه `groupIds=1` و در دسترس همان نماینده باشد. UUID و Sub ID را در برنامه به‌صورت تصادفی و منحصر‌به‌فرد تولید کنید؛ مقادیر ثابت نمونه را برای مشتری واقعی تکرار نکنید. `totalGB=10737418240` یعنی ۱۰ گیبی‌بایت و `renewalDuration=2592000000` یعنی ۳۰ روز بر حسب میلی‌ثانیه. `expiryTime` باید زمان واقعی انقضا باشد، نه مدت ۳۰ روز؛ نمونهٔ زیر شروع فوری را نشان می‌دهد.

```bash
CLIENT_UUID="$(python3 -c 'import uuid; print(uuid.uuid4())')"
SUB_ID="$(python3 -c 'import secrets; print(secrets.token_urlsafe(18))')"
EXPIRY_MS="$(python3 -c 'import time; print(int(time.time()*1000)+30*86400000)')"
SETTINGS="$(python3 -c 'import json,sys; print(json.dumps({"clients":[{"id":sys.argv[1],"email":"alice","enable":True,"subId":sys.argv[2],"totalGB":10737418240,"expiryTime":int(sys.argv[3]),"renewalDuration":2592000000,"limitIp":0,"reset":0}]}))' "$CLIENT_UUID" "$SUB_ID" "$EXPIRY_MS")"
curl -sS -b "$JAR" -H 'X-Requested-With: XMLHttpRequest' \
  -X POST "$BASE/panel/api/inbounds/addClient" \
  --data-urlencode 'id=3' --data-urlencode 'groupIds=1' \
  --data-urlencode "settings=$SETTINGS"
```

اگر گروه شامل چند پروتکل است، فیلدهای اتصال موردنیاز **همهٔ آن‌ها** را در درخواست بفرستید؛ مثلاً گروه VLESS و Shadowsocks هم UUID و هم رمز معتبر لازم دارد. فیلد خالی یا نامعتبر باعث رد کل درخواست پیش از ساخت و کسر اعتبار می‌شود. کلیدهای دستگاه WireGuard که پنل خودش می‌سازد از این فیلدهای دستی جدا هستند.

در درخواست چند گروه، `groupIds` را برای هر گروه تکرار کنید. سرور اجتماع ورودی‌های گروه‌ها را محاسبه و دسترسی و سازگاری آن‌ها را بررسی می‌کند؛ در حالت گروهی، `id` ورودیِ هدف باید عضو همان مجموعه باشد. از `inboundIds` برای دورزدن گروه‌ها استفاده نکنید. در پایان موفقیت پاسخ و سپس فهرست/وضعیت کاربر را بررسی کنید؛ خطای سهمیه، ظرفیت یا نام تکراری را به مشتری «سرویس ساخته شد» نمایش ندهید.

نمونهٔ VLESS برای همهٔ پروتکل‌ها کافی نیست. شناسهٔ ورودی پروتکل‌محور است: VMess/VLESS معمولاً UUID در `id`، Trojan و Shadowsocks رمز در `password`، Hysteria مقدار `auth` و VPNهای نام‌کاربری/رمز فیلدهای متناسب خود را می‌خواهند. برخی پروتکل‌ها کلید یا آدرس اختصاصی می‌سازند و رمز Shadowsocks 2022 قالب خاص دارد. قبل از پیاده‌سازی هر پروتکل [مرجع کامل API](../api-reference.md) و تنظیمات همان ورودی را بررسی و با دادهٔ آزمایشی تست کنید.

## ۶. ویرایش، تغییر وضعیت و اشتراک

برای ویرایش، ابتدا رکورد و عضویت مجاز را بخوانید. `POST /panel/api/inbounds/updateClient/:clientId` در بدنه به `id` ورودی و `settings` به‌شکل رشتهٔ JSON شامل `clients` نیاز دارد. `clientId` را از **همان membership** بخوانید؛ بسته به پروتکل UUID، رمز، شناسه یا مقدار دیگری است. برای تغییر صرفِ اطلاعات حساب، مسیر فرانت‌اند نماینده اطلاعات موجودِ کلاینت آن ورودی را نگه می‌دارد و فقط فیلد موردنظر را تغییر می‌دهد؛ ارسال آبجکت ناقص یا خالی ممکن است تنظیمات مهم را تغییر دهد. برای تغییر گروه، `groupIds` تکرارشونده را صریحاً بدهید؛ حذف عمدی همهٔ دسترسی‌ها برای نماینده مجاز نیست. حذف فیلد گروه در ویرایش معمولی، انتخاب گروه را حفظ می‌کند.

برای فعال/غیرفعال‌کردن **یک عضویت روی یک ورودی**، با مجوز ویرایش و دسترسی به هر دو هدف:

```sh
curl -sS -b "$JAR" -H 'X-Requested-With: XMLHttpRequest' \
  -X POST "$BASE/panel/api/inbounds/3/setMembershipEnable/alice" \
  --data-urlencode 'enable=false'
```

این سوییچ با وضعیت کلی حساب متفاوت است؛ فعال‌کردن عضویت، سهمیهٔ تمام‌شده یا مسدودبودن نماینده را دور نمی‌زند.

برای ساخت لینک اشتراک، از **آدرس کامل سابِ پیکربندی‌شده توسط مدیر** و `subId` حساب استفاده کنید. پورت، دامنه و مسیر ساب می‌تواند با آدرس پنل فرق داشته باشد؛ آن را حدس نزنید. در نصب‌های دارای لینک قدیمیِ مهاجرت‌شده، `legacySubId` و قواعد آن نصب را نیز در نظر بگیرید. لینک ساب یک اطلاعات دسترسی است: فقط به صاحب سفارش و به‌صورت خصوصی در تلگرام ارسال شود. اشتراک دو حساب با `subId` یکسان می‌تواند کانفیگ‌های هر دو را نشان دهد، اما سهمیه‌هایشان را ادغام نمی‌کند؛ برای مشتریان مستقل شناسه‌های تصادفی جدا تولید کنید.

## ۷. تمدید، ریست و حذف

**تمدید** بستهٔ قبلی را از نو شروع می‌کند: مصرف فعلی را صفر می‌کند، مدت اصلی ثبت‌شده را از زمان فعلی شروع می‌کند و حساب را فعال می‌کند؛ حجم بسته، شناسهٔ ساب، رمزها و انتخاب‌های دسترسی حفظ می‌شوند. برای حساب قدیمی که مدت اصلی‌اش ثبت نشده، `renewalDuration` را به میلی‌ثانیه بفرستید. برای مدت ثبت‌شده، مقدار ارسالی در صورت وجود باید با مدت ثبت‌شده برابر باشد. حساب بدون انقضای زمانی فقط صفر را می‌پذیرد. مدت جدید را حدس نزنید؛ از نماینده بپرسید.

```sh
# مدت ذخیره‌شده را استفاده کن:
curl -sS -b "$JAR" -H 'X-Requested-With: XMLHttpRequest' \
  -X POST "$BASE/panel/api/inbounds/renewClient/alice"
# برای حساب قدیمی با مدت نامعلوم، ۳۰ روز:
curl -sS -b "$JAR" -H 'X-Requested-With: XMLHttpRequest' \
  -X POST "$BASE/panel/api/inbounds/renewClient/alice" \
  --data-urlencode 'renewalDuration=2592000000'
```

نماینده برای تمدید به `users.update` و `users.reset_usage` در محدودهٔ مجاز نیاز دارد. بسته به روش حسابداری، تمدید می‌تواند از اعتبار هزینه کند؛ مصرف مادام‌العمر نماینده پاک نمی‌شود. عضویت غیرفعال و مسدودیت نماینده با تمدید دور زده نمی‌شوند.

**ریست مصرف** با مجوز `reset_usage` از مسیر `POST /panel/api/inbounds/:id/resetClientTraffic/:email` انجام می‌شود. `id` باید ورودی قابل دسترسی کاربر باشد. ریست، مصرف دوره را پاک می‌کند؛ تمدید تاریخ یا فعال‌کردن کاربر نیست و ممکن است هزینه داشته باشد.

**حذف** از مسیر `POST /panel/api/inbounds/:id/delClientByEmail/:email` به مجوز حذف و دسترسی لازم نیاز دارد. شناسهٔ ورودی واقعی و ایمیل URL-encode‌شده را بفرستید. این مسیر به ورودی مشخص مربوط است؛ حساب چندورودی را با فرض اینکه یک فراخوانی همهٔ عضویت‌ها را حذف می‌کند پاک نکنید. حذف ممکن است روی بازپرداخت اعتبار اثر بگذارد. در نسخهٔ دارای اصلاح حذف چندورودی، `GET /panel/api/inbounds/multiDeleteCapability` مقدار `obj.preservesSharedTraffic=true` برمی‌گرداند؛ اگر این قابلیت موجود نبود برای حذف خودکار چندورودی اقدام نکنید. همهٔ عضویت‌های واقعی را بخوانید و هر کدام را جداگانه حذف و پس از هر درخواست بررسی کنید. این عملیات اتمیک نیست: اگر قطع یا خطا رخ داد، عضویت‌های باقی‌مانده و وضعیت حساب را پیش از ادامه بررسی کنید. تا حذف آخرین عضویت، مصرف و IPهای مشترک حفظ می‌شوند.

## ۸. عملیات گروهی

`POST /panel/api/inbounds/bulkPreview` پیش‌نمایش و `POST /panel/api/inbounds/bulkUpdateClients` اجرا را می‌دهد. بدنهٔ هر دو، فیلد فرم `data` شامل یک **رشتهٔ JSON** است، نه صرفاً JSON آزاد. مثال برای افزودن روز به کاربران مجاز:

```sh
curl -sS -b "$JAR" -H 'X-Requested-With: XMLHttpRequest' \
  -X POST "$BASE/panel/api/inbounds/bulkPreview" \
  --data-urlencode 'data={"op":"addDays","days":30,"targets":[{"inboundId":3,"email":"alice"}]}'
```

پس از نمایش پیش‌نمایش و تأیید نماینده، همان قالب را به `bulkUpdateClients` بفرستید. عملیات موجود شامل `addDays`، `subDays`، `addTraffic`، `subTraffic`، `enable`، `disable`، `delete`، `freeze` و `unfreeze` است؛ برای حجم از `amountBytes` و برای روز از `days` استفاده می‌شود. فیلدها و پاسخ‌های کامل در [مرجع API، بخش عملیات گروهی](../api-reference.md#11-bulk-operations) آمده‌اند. نتیجهٔ اجرا را از نظر تعداد اعمال/رد بررسی کنید؛ پیش‌نمایش رزرو اعتبار نیست و قیمت در زمان اجرا دوباره محاسبه می‌شود. عملیات تابع مجوز و محدوده است؛ برای نمایندهٔ معمولی جابه‌جایی گروهی عضویت‌ها مجاز نیست.

## ۹. اتصال به تلگرام و جلوگیری از سفارش تکراری

یک جریان پیشنهادی برای ربات فروش:

1. ربات کاربر تلگرام را با شناسهٔ عددی او شناسایی کند و محصول، قیمت، مدت و گروه مجاز را از تنظیمات خودش بخواند.
2. سفارش را با شناسهٔ یکتا ذخیره کند؛ سپس پرداخت را طبق پاسخ معتبر درگاه تأیید کند. خودِ پیام کاربر یا اسکرین‌شات پرداخت، تأیید درگاه نیست.
3. برای هر پرداخت فقط یک عملیات ساخت یا تمدید انجام دهد. وضعیت سفارش و شناسهٔ کاربر پنل را در دیتابیس ربات ذخیره کند تا دریافت دوبارهٔ اعلان پرداخت باعث صدور دوباره نشود.
4. پس از موفقیت API، وضعیت را دوباره بخواند و لینک ساب را فقط به چت خصوصی خریدار بفرستد. در صورت نامعلوم‌بودن نتیجهٔ درخواست نوشتن، پیش از تکرار، وضعیت کاربر/سفارش را بررسی کند؛ تکرار کورکورانه ممکن است هزینه یا سرویس دوباره ایجاد کند.
5. دکمه‌های «مصرف»، «تمدید» و «پشتیبانی» را فقط برای مالک همان سفارش فعال کند. شناسهٔ مشتری در callback تلگرام را با دیتابیس ربات و `from.id` تطبیق دهد؛ پارامتر دستکاری‌شدهٔ پیام نباید اجازهٔ دسترسی به مشتری دیگر بدهد.
6. زمان درخواست و اتصال، خطاها و محدودیت تعداد درخواست را مدیریت کند؛ در صورت منقضی‌شدن نشست ورود مجدد انجام دهد و از ارسال رمز، توکن، کوکی و لینک ساب به لاگ خودداری کند.

ربات و درگاه پرداخت باید جداگانه نصب و پیکربندی شوند؛ این سند ادعای سازگاری همهٔ ربات‌های آمادهٔ 3X-UI یا PasarGuard را ندارد. قبل از فروش واقعی، ساخت، خواندن، تمدید، محدودیت نقش و مدیریت خطای نشست را با حساب و مشتری آزمایشی بررسی کنید.
